How Kaser Web works

Your Kaser games run in Chrome and Safari, on the Mac and the iPad, using Everett's own interpreter. This page follows each piece, from the game file on your disk to the pixels and sounds in the browser.

The big picture

There are two halves. On the Mac, a small Python program (server.py) reads the games you own and keeps your saves. In the browser, a set of web pages runs each game with Everett's KINT interpreter, translated to WebAssembly, a form of machine code that browsers can run at near-native speed.

The server never runs any game code. It only hands out files and stores what the games write. All the work of running a game happens inside the browser, which is why a game you've downloaded keeps working on the iPad with the Mac switched off.

What a Kaser game is

Everett writes each game in C, but it isn't compiled for Windows or the Mac. He ported a C compiler to produce instructions for his own virtual CPU, and his assembler and linker turn those into a file called MAIN.KE. A separate program, the KINT interpreter, reads MAIN.KE and carries out its instructions, much as a Java runtime runs Java bytecode. The Mac app you bought is that interpreter packaged with MAIN.KE and the game's pictures (BMP, JPG), sounds (WAV), music (MID), fonts, dialog layouts (*.UI) and puzzle files, all inside Contents/Resources.

That design is what made the port practical. Port the interpreter once, and every game built on it works, with no changes to the games themselves.

KINT 5 · 37 games

Sherlock, the Knarly series, Hero's Hearts and the rest. Their MAIN.KE starts with the letters KASMB. They run on the KINT 1–5 interpreter, whose C source came with Everett's KINT 5 kit.

KINT 6 · 3 games

Crocotile, Lair of Moriarty and Occam's Quilt. Their files start with KINT6 and need a newer, different virtual CPU. Its C source comes with Everett's KINT 6 kit.

The interpreter in the browser

Everett's C code, nearly unchanged

The KINT 5 interpreter has three parts that matter: pmach.c (the virtual machine, plus all the drawing, which it does itself in software), float.c (decimal numbers) and djpeg.c (JPEG pictures). None of them depend on Windows, so they are compiled as they are.

The fourth part, main.c, is where Windows comes in: windows, the message pump, files, sound, timers. That file is left out and replaced by a platform layer written for the browser: engine/k5/kplat.c in C, backed by engine/k5/kint_lib.js in JavaScript. It keeps the same message queue, idle handling and coordinate rules as Everett's main.c, so MAIN.KE sees the world it expects.

The few edits to Everett's own files are made by engine/patch_k5.py on copies, never on the originals. Each edit is an exact find-and-replace that must match exactly once, so if Everett ships a new version that no longer matches, the build stops instead of producing something subtly broken. KINT 6 works the same way: patch_k6.py lifts the portable parts of its main.c (file loader, message queue, memory manager) into kmain6.c, and kplat6.c supplies the browser side. KINT 6 also brings two small libraries for PNG pictures.

Compiled to WebAssembly

Emscripten (emcc) compiles the C into web/kint5.wasm and web/kint6.wasm, plus a small JavaScript loader for each. One detail made this a natural fit: the virtual machine keeps real memory addresses in its 32-bit registers, as it did on 32-bit Windows, and WebAssembly also uses 32-bit addresses. So the original code works without reworking how it stores pointers.

A loop that never lets go

A Windows program sits in a loop forever: wait for a message, handle it, repeat. Web pages work the other way round. A page's code must keep returning control to the browser, or the page freezes. Rewriting Everett's loop inside out would mean changing the interpreter deeply.

The port avoids that by running each game in a Web Worker, a background thread with no screen of its own. A worker is allowed to block, so the interpreter's loop runs exactly as written. Three consequences follow:

  • Input through shared memory. The game page writes mouse, key and touch events into a small ring buffer in a SharedArrayBuffer, memory both threads can see. When the game has nothing to do, it waits with Atomics.wait: the thread sleeps until the page signals a new event or the game's next timer is due. That is the browser equivalent of Windows' GetMessage.
  • Files must be instant. The game expects fopen and fread to return straight away. So file calls either use synchronous requests to the server, or read from the downloaded copy, which is already on the device (see Files and saves).
  • Output goes out as messages. Screen updates, sounds, the window title, the mouse cursor shape, "open this web page" and "the game has exited" are posted to the game page, which acts on them.

Why HTTPS matters here. Browsers only allow SharedArrayBuffer on a page that is both secure (HTTPS, or localhost) and "cross-origin isolated". The server sends the two headers that grant that isolation (Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy) with every response. Without HTTPS, the iPad couldn't run the games at all.

From click to play

Here's what happens when you click Sherlock in the launcher:

  1. The launcher checks whether Sherlock is already kept on this device, and whether the server has a newer version. If the stored copy is out of date, it downloads the new one first.
  2. It opens /play?g=Sherlock in a new window named after the game. If that window already exists, it brings it to the front instead, so two copies can't overwrite each other's saves. In the iPad Home Screen app, the game replaces the launcher instead.
  3. The game page (play.js) sets up the canvas, the input ring buffer and sound, then starts worker.js, telling it the game's name and whether to use the copy on this device.
  4. The worker loads kint5.wasm or kint6.wasm, connects it to a file system (the server's or the device's), and calls the interpreter's entry point, kp_main.
  5. The interpreter opens pgm/MAIN.KE, the same file the Mac app runs, and starts carrying out Sherlock's code. From here on, the worker never stops.
  6. Sherlock reads its settings from app/, draws its window and posts the first screen. Your clicks flow in through the ring buffer; screens and sounds flow back out.
  7. When you choose Exit, the game saves its state and the worker sends exit. The page waits until every save has been written, then closes the window.

Screen, sound, music

Screen

The interpreter draws into its own pixel buffer, as it did on Windows. The platform layer tracks which rectangles changed and posts only those to the page, which paints them onto a <canvas>. The canvas fills the window and is scaled with sharp, blocky pixels so text stays crisp.

Sound effects

WAV files, from disk or built into the game's memory, are decoded by the browser's Web Audio system and played. Browsers allow sound only after you've interacted with the page, which is why sound starts with your first click or tap.

Music

The games' background music is MIDI. Browsers can't play MIDI themselves, so SpessaSynth, a software synthesizer, plays it with the General MIDI instrument bank built into macOS (gs_instruments.dls). The server provides that bank at /api/soundbank, and the iPad keeps a copy for offline play. When a song ends, the game is told, as Windows would tell it, so it can start the next one.

Files and saves

KINT games see two folders. pgm/ is the game's own folder (read-only; on the Mac, the .app's Contents/Resources). app/ is its save folder. Names are matched without regard to case, as on Windows, because the games were written for Windows.

The worker's file calls go through web/fs.js, which has two interchangeable back ends:

serverFS

Straight from the Mac

Each file call becomes a synchronous request to /api/g/<game>/…: read, stat, list, write, make or remove a folder. Saves land in saves/<game>/ on the Mac. Files the game has already read are cached, so each one is fetched only once per session.

localFS

From this device

Reads come from the game's pack file, already loaded. Writes are kept in memory, so the game never waits, and the page saves them to IndexedDB in the background. Before the window closes, the page waits until every save has been stored.

Saves from the native Mac apps (in ~/Library/Application Support/Everett Kaser Software/) can be copied into saves/ once with tools/import_native_saves.py. From then on the two are separate. Playing in the browser doesn't change the native apps' saves, and the other way round.

The server

server.py uses only Python's standard library, so there's nothing to install. When it starts, it looks in games/ for apps containing a MAIN.KE, works out which interpreter each needs from the file's first bytes, and listens on port 8765. Each connection gets its own thread, so a slow iPad never holds up the Mac.

Playing offline

Three browser features let a game run with the Mac switched off:

  • The service worker (sw.js) keeps a copy of the app itself: pages, scripts, interpreters, icons and the music bank. When you open the launcher, it serves those from the copy. For the game list, it asks the server first and gives up after 2.5 seconds, falling back to the last list it saw and marking it as offline. That mark is what shows the "can't reach the game server" notice.
  • The download worker (download.js) fetches a game's index, then streams its data into a single pack file in the browser's private file system. The index (which file starts where in the pack) goes into IndexedDB. A game made of between 130 and 1,000 files, up to about 80 MB, becomes one file on the device.
  • IndexedDB holds your saves on that device. On a game's first download they're copied from the Mac, so your progress carries over. After that, saves on the device stay there; sending them back to the Mac isn't built yet.

Downloads happen when Keep games on this device when I play them is ticked, or when you use Download all games. When the server reports a newer version of a game, its fingerprint changes and the launcher downloads it again the next time you play it.

Storage belongs to the address. Browsers keep storage separate for each site address, and https://192.168.1.20:8765 and https://192.168.1.21:8765 (example addresses) count as different sites. That's why changing the Mac's IP address means downloading again, and why it's worth asking your router to always give the Mac the same address.

Network and HTTPS

Listening

The server listens on every network connection the Mac has, over both IPv4 and IPv6, so an iPad on the same Wi-Fi can reach it at the Mac's address, for example https://192.168.1.20:8765. The server prints the right address when it starts. The macOS firewall must allow Python to accept incoming connections.

The certificate

HTTPS needs a certificate the browser trusts. mkcert made a private certificate authority on your Mac, a "root" certificate that exists only on your machines, and used it to sign cert.pem for your Mac's addresses. A device trusts the server only if it trusts that root. On an iPad, that means installing the rootCA.pem profile, then turning on full trust under Settings → General → About → Certificate Trust Settings.

Skipping the full-trust step causes a confusing symptom. The iPad refuses the server's certificate, but the launcher runs from the service worker's copy, so no warning appears. The page just loads forever, then says it can't reach the game server. Once the root is trusted, every certificate from the same mkcert is accepted automatically, including new ones made when the Mac's address changes.

Typing http:// by mistake

Every HTTPS connection starts with a "handshake" message whose first byte is 0x16. The server peeks at the first byte of each new connection. If it's anything else, the visitor typed http://, so the server answers in plain HTTP with a redirect to the same page over https://.

Touch on the iPad

The games were made for a mouse, so the game page turns touches into mouse actions:

A mouse or trackpad connected to the iPad works as a normal mouse. The page blocks the iPad's own long-press features on the game (text selection, the magnifier, the callout menu) so they don't get in the way. Added to the Home Screen, the launcher runs as a full-screen app.

Building and testing

engine/build.sh rebuilds both interpreters: it runs the two patch scripts on Everett's sources in kint_src/, then emcc twice, writing web/kint5.* and web/kint6.*. engine/build.sh debug builds a slower version with extra checks, for tracking down crashes.

tools/cdp.mjs drives a hidden copy of Chrome: it opens a page, waits, clicks, types, runs checks and takes screenshots. It was used to confirm that all 40 games reach their opening screens, online and offline, and to test changes to the launcher.

Git tracks only the port's own files. Your games, saves, certificates, Everett's KINT source and the built interpreters stay out of it.
