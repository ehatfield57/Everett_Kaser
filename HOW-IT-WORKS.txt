HOW KASER WEB WORKS
===================

A short summary of how your Everett Kaser games run in Chrome and Safari.
The server runs on a Mac or a Windows PC; any device with a modern
browser can play (Mac, Windows, iPad, iPhone, Android).
For the full explanation, with a diagram, open HOW-IT-WORKS.html in a
browser (double-click it in Finder).


A Kaser game is a program plus an interpreter
---------------------------------------------
Everett writes each game in C, but it isn't compiled for Windows or the
Mac. He ported a C compiler to produce instructions for his own virtual
CPU, and his assembler and linker turn those into a file called MAIN.KE.
A separate program, the KINT interpreter, reads MAIN.KE and carries out
its instructions. Each Mac app is that interpreter bundled with the
game's MAIN.KE and its pictures, sounds, music, fonts and puzzles
(inside Contents/Resources). The Windows version is the same interpreter
as an .exe in a plain game folder, with the same files beside it.

37 games use KINT 5 (MAIN.KE starts with "KASMB"). Crocotile, Lair of
Moriarty and Occam's Quilt use KINT 6, a newer interpreter.


The port moves the interpreter, not the games
---------------------------------------------
Everett's C code for the interpreter (pmach.c, float.c, djpeg.c, and the
KINT 6 equivalents) is compiled, nearly unchanged, to WebAssembly: machine
code that browsers can run at near-native speed. The result is
web/kint5.wasm and web/kint6.wasm.

Only his Windows-specific part (main.c: windows, files, sound, timers) is
left out and replaced with a browser version: engine/k5/kplat.c and
engine/k5/kint_lib.js (engine/k6/kplat6.c for KINT 6). The few edits to
Everett's own files are exact find-and-replace patches applied to copies
by engine/patch_k5.py and engine/patch_k6.py.

Because the interpreter is ported, all 40 games run unmodified, using the
same MAIN.KE files as the Mac apps.


Each game runs in a background thread
-------------------------------------
A Windows program loops forever: wait for a message, handle it, repeat.
Web pages can't do that without freezing, so each game runs in a Web
Worker (a background thread), where the interpreter's loop works exactly
as Everett wrote it.

  - Your clicks, keys and touches reach the game through a small piece of
    memory both threads share (a SharedArrayBuffer). While it has nothing
    to do, the game sleeps until an event arrives or a timer is due.
  - Screen updates, sounds, the window title and "the game has exited"
    come back to the game page as messages.
  - File reads have to be instant, so they either ask the server directly
    or read from the copy of the game already stored on the device.

Browsers only allow that shared memory (and the audio engine, and storing
games on the device) on secure pages that send two special headers. A page
counts as secure at http://localhost on the computer itself, or over
https:// anywhere. That's why tablets and phones need HTTPS.


Screen, sound and music
-----------------------
  - Screen: the interpreter draws into its own pixel buffer, as on
    Windows. Only the changed rectangles are sent to the page, which paints
    them onto a canvas that fills the window.
  - Sound effects: WAV files, played with the browser's Web Audio.
    Browsers allow sound only after your first click or tap.
  - Music: the games' MIDI music is played by SpessaSynth, a software
    synthesizer, using the General MIDI instruments built into the
    server's computer (gs_instruments.dls on macOS, gm.dls on Windows).


server.py only hands out files
------------------------------
server.py uses Python's standard library, plus the cryptography package
to make its certificate for tablets and phones. It:
  - finds the games (Mac apps linked in games/, or the Windows game
    folders where they're installed) and works out which interpreter each
    one needs,
  - serves the launcher, the game page and the game files,
  - stores everything the games write in saves/<game name>/,
  - streams a whole game as one "pack" when a device downloads it.

It never runs any game code. All of that happens in the browser.


Offline play
------------
Three things let a downloaded game run with the Mac switched off:

  - The service worker (web/sw.js) keeps a copy of the app itself:
    pages, scripts, interpreters, icons and the music instruments.
  - Each downloaded game becomes one pack file in the browser's private
    file system, with its index in the browser's database (IndexedDB).
  - Your saves on that device live in the browser's database too. On a
    game's first download they're copied from the Mac, so progress carries
    over. Saves made on the device stay there (sending them back to the Mac
    hasn't been built yet).

Each address keeps its own storage. https://192.168.1.20:8765 and
https://192.168.1.21:8765 (example addresses) count as different sites,
which is why changing the Mac's IP address means downloading again. It's
worth asking your router to always give the Mac the same address.


HTTPS and the certificate
-------------------------
The first time it starts, the server makes a private certificate
authority (a "root" certificate) that exists only on that computer, and
uses it to sign a certificate for the computer's names and addresses
(all kept in the tls folder). When the address changes, it signs a new
one by itself.

Each other device must trust that root once. When a device that doesn't
yet trust it opens the server's http:// address, the server answers with
a "Set up this device" page instead of the games. (It can tell, because
an HTTPS connection always starts with the byte 0x16.) The page offers
the root certificate to download and shows the steps for Android,
iPhone/iPad or a computer. It then asks the server over https:// in the
background; once that works, the device trusts the server, and the page
moves to the https:// address. After that, the http:// address forwards
there by itself. The computer running the server can always use
http://localhost, so it needs no setup.

The address the server prints for other devices uses the next port up
(http://192.168.1.20:8766), which only ever shows the setup page.
Chrome's "Always use secure connections" setting tries https:// before
http://. On port 8765 that attempt meets the certificate the device
doesn't trust yet, and Chrome gives up with ERR_TOO_MANY_RETRIES. Port
8766 hangs up on any https:// attempt, so Chrome falls back to http://
(after asking, in that mode) and the setup page appears.

Android Chrome with that setting on still gives up on 8766, so there is
a second way in: https://192.168.1.20:8765/setup. Chrome warns that the
connection isn't private; tap Advanced, then Proceed. Chrome loads a page
reached that way but refuses to register its service worker, so the
setup page (and the launcher) try to register one: if that fails, the
device doesn't trust the certificate yet, and the setup steps appear.

On an iPad, skipping the "full trust" step (Settings > General > About >
Certificate Trust Settings) causes a confusing symptom: the launcher
runs from the service worker's copy, so no warning appears. The page
just loads forever, then says it can't reach the game server.

If cert.pem and key.pem made with mkcert are present, the server uses
those instead, and the setup page offers mkcert's root.


Touch on the iPad
-----------------
  Tap                        left click
  Touch and drag             left-button drag
  Touch and hold (~0.5 s)    right click (a ring flashes)
  Two-finger tap             right click
  Swipe, with the swipe button (four-way arrow) on    arrow keys
                             (on by default for the Hero games)
  Keyboard button            opens the on-screen keyboard
  Spread / pinch two fingers zoom in / out (stays zoomed when you let go)
  Move two fingers           look around while zoomed in
  Zoom-out button (circled minus)    back to the whole screen
  On an iPhone the game is laid out at desktop size and shrunk to fit;
  zoom in to reach the small icons.


Building and testing
--------------------
  engine/build.sh          rebuilds both interpreters (needs emcc)
  engine/build.sh debug    a slower build with extra checks
  tools/cdp.mjs            drives a hidden Chrome to test that games start

Git tracks only the port's own files. Your games, saves, certificates,
Everett's KINT source and the built interpreters stay out of it.

Everett's KINT license allows private use only. The port is for playing
games you own, on your own machines; the interpreter is Everett's work.
